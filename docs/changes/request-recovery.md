# 请求失败恢复与诊断

重复标签流仍由原检测器识别、关闭并丢弃。若本回合仍有步骤额度，Kernel 保留已提交的消息和工具结果，追加有界恢复提示，再请求一次；整回合最多一次，不因中间成功调用工具而重置。取消会阻止恢复请求。已执行的工具不重放，坏流中的调用不执行；再次重复以 `LLM_REPETITIVE_OUTPUT`／`invalid_response` 结束，并报告恢复次数。

原生图片仍是请求临时内容，不进入持久历史。重复流未形成有效响应时，恢复请求会重新带上该图片；有效响应后消费，后续普通步骤不再附图。恢复增加最多一次模型请求，并占用现有步骤额度；这不保证模型一定恢复，也不表示最终文件已经交付。

历史压缩后仍超预算时，`CONTEXT_INPUT_BUDGET_EXCEEDED`／`context_length` 报告实际历史额度及估算值，同时区分总输入额度、额外消息和临时图片开销。此时 Skill 正文尚未投影；后续资料组装仍执行独立的预算检查。原生图片按已有像素估算，Base64 不按普通文本计入。

图片代理分析失败保留原 `IMAGE_REQUEST_FAILED` 工具错误码，新增安全的 provider 分类、HTTP 状态、是否可重试和 request ID。未知 400／422 归为请求参数错误；无明确分类的异常使用静态说明，不将原始异常字符串或图片请求体放入工具结果。明确不支持图片能力的响应继续走已有兼容分支。

以上机制只处理请求恢复和诊断。模型提早结束、渲染参数错误、权限阻断与最终产物缺失仍需按各自契约检查，不能以回合正常结束代替产物验收。provider 的 reasoning 兼容配置属于运行 profile，应在新实验中冻结并验证主调用及辅助调用实际参数，不能写入业务 Skill。

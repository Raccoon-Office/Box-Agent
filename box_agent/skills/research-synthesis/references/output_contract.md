# Compact Research Output Contract

## Default Files

```text
research/
  {topic}_research.md
  {topic}_evidence.json
  qa/{topic}_research_check.json
```

Only the narrative and evidence ledger are authored directly. The QA report is
generated by the validator. Legacy facet/dimension/cross-verification files may
remain, but new work does not need to create them.

## Narrative

`{topic}_research.md` uses whatever headings best fit the question. It should
make the findings, conflicts, conclusions, and material source limitations easy
to understand. Footnotes are welcome but not mandatory, and missing footnote
definitions are advisory rather than a delivery failure.

## Evidence Ledger

Use a compact JSON object:

```json
{
  "schema_version": 1,
  "topic": "topic-slug",
  "evidence": [
    {
      "entity": "Example Corp",
      "claim": "Example Corp launched Product One in 2026.",
      "source_url": "https://example.com/news/product-one",
      "source_type": "first_party",
      "evidence_excerpt": "Example Corp launched Product One in 2026.",
      "confidence": "high",
      "status": "verified"
    }
  ]
}
```

For a `verified` row, only these fields are required:

- `claim`: the fact to hand off;
- `source_url`: the exact opened article, report, filing, or data page;
- `evidence_excerpt`: a short excerpt copied from that page;
- `status`: `verified`.

`entity`, `source_type`, and `confidence` are optional and improve downstream
presentation. Omitted values default to the topic, `secondary`, and `medium`.

Use `conflicting` or `unverified` for material that must not enter factual
downstream copy. Extra metadata is allowed but is not required or deeply
validated. In particular, no `fact_key`, normalized value, time/scope/unit,
publication timestamp, target-entity registry, or per-agent shard is required.

For quantitative, time-sensitive, forecast, ranking, or disputed facts,
`fact_key`, `fact_value`, `time_basis`, `scope`, and `unit` are strongly
recommended. Reuse the same `fact_key` and scope when two sources address the
same fact, and use distinct `time_basis` values for legitimate historical
changes. This lets the validator distinguish a new snapshot from a real
contradiction without making metadata omissions a delivery blocker.

Search result pages and origin homepages are not valid verified sources. The
runtime presentation policy additionally checks that the exact page and excerpt
were actually read during the run.

The validator excludes a verified row when its excerpt omits a claim number or
clearly reverses increase/decrease, above/below, or affirmed/negated meaning. It
also groups rows describing the same fact and excludes the entire unresolved
group when values, directions, or units conflict. These findings are reported
as gaps and downgrade delivery to `partial` or `framework`; they do not trigger
a formatting repair loop.

## Validation Report

The generated report exposes `presentation_handoff` schema v1:

- `delivery_mode`: `full`, `partial`, `framework`, or `invalid`;
- `verified_facts`: verified rows safe for factual downstream use;
- `gaps`: excluded rows and advisory issues;
- `quality_summary`: compact diagnostic counts;
- `context_files`: narrative files available as context.

Only missing/unreadable core artifacts make the handoff `invalid`. Invalid
verified rows are excluded and reported as gaps; they do not force a formatting
repair loop. A valid `partial` or `framework` report exits successfully.

If the narrative or ledger changes after validation, rerun the validator once
so the report is fresh.

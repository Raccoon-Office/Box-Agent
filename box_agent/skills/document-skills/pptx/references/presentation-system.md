# Shared presentation system

The theme declares an identity; the layout declares information structure. The
presentation system combines them without a theme-specific geometry patch.
This applies to canvas compositions (`open`, `editorial`, and the editorial
cover's `poster`). Explicit traditional compositions retain their family shell.
Previously saved HTML is self-contained and changes only when regenerated.

## Ownership

| Concern | Source of truth |
| --- | --- |
| Palette, display/body/label font families, shape and style traits | `themes/*.json`, including catalog files |
| Theme voice, supported style traits, content density, preferred canvas composition | `runtime/presentation-system.js` |
| Shared scale, surface foregrounds, semantic layout adaptation and reading rhythm | `runtime/presentation-system.css` |
| Fields, limits, semantic geometry and text roles | `layouts/registry.js` |
| Exact measured heading/value fitting | `runtime/text-fit.js` |
| Content-linked hand-drawn annotations | `runtime/sketch-runtime.js`, enabled by the `sketch` voice |
| Generated theme/layout discovery contract | `layouts/manifest.json`, generated by `scripts/build_layout_manifest.js` |
| All-theme/all-layout maintenance check | `scripts/render_theme_matrix.js` |

The old named-theme and composition rules in `deck.css` and `composition.css`
are scoped with `:where(:not(.expressive-slide, .expressive-slide *))`. The guard
has zero specificity and preserves the traditional cascade while excluding
canvas subjects. Do not add new theme-id overrides to the presentation layer.
Palette variables are emitted on each canvas as well as on `:root`, so legacy
body-level variables cannot change one surface without its matching foreground.

## Adding or adjusting a theme

Run the repository commands below from the repository root. Keep review artifacts
under the conversation-selected `<PRESENTATION_DIR>/qa/`, outside the Skill source
directory. Substitute the absolute directory using the Skill's literal path
quoting rules; do not add an automatic `output/` layer.

1. Add or edit its existing theme JSON contract. Keep palette, typography,
   shape, style and composition declarations together. No new CSS selector is
   needed for a theme id. Existing catalog and individual theme files use the
   same resolver; omitted style traits inherit shared defaults.
2. Choose supported `style` values from `STYLE_VALUES`. Heading and composition
  traits resolve a voice; voices affect weight, rules and reading rhythm.
   Fonts and colors remain the theme's own choices. A new trait requires a
  shared implementation and a regression test rather than an id exception.

The selected composition family supplies a coarse reading rhythm (for example,
editorial columns); it does not replace the semantic layout. Traditional family
chrome and its historical variants remain available through the traditional
composition mode. Theme previews use the shared canvas default; the separate
composition-family atlas demonstrates those traditional shells explicitly.
3. Regenerate discovery and run the matrix for that theme. Review the rendered
   pages as well as the numbers: valid geometry alone is not visual approval.

```bash
node box_agent/skills/document-skills/pptx/scripts/build_layout_manifest.js
node box_agent/skills/document-skills/pptx/scripts/render_theme_matrix.js --out '<PRESENTATION_DIR>/qa/pptx-theme-review' --themes NEW_THEME_ID --check --screenshots
```

## Adding or adjusting a layout

- Define semantic fields and their real limits in the registry. Text fields
  declare `display`, `heading`, `lead`, `body`, `label`, `caption`, `source`,
  `metric`, or `metric-or-point`. `metric` means a value with a unit that should
  stay together; a conceptual proof sentence is not a metric.
- Render through `slideFrame` and `editableText` / `editableTableCell`. They
  attach roles and density consistently, preserve editability and give new
  layouts the shared canvas behavior. Keep direction, counts and relationships
  inside the semantic layout; do not invent ordering to create variety.
- A filled semantic region declares `data-presentation-surface="base|surface|tint|accent"`.
  This binds fill and text foreground together. Use explicit chart/heatmap
  color logic for encoded data intensities instead of flattening them to one
  surface role.
- Sparse content gets a larger scale; regular and dense content use smaller
  budgets. Density is recomputed from fields after editing and survives saved
  HTML. Do not truncate text, change values or hide unique content to make it
  fit. An identical eyebrow can be hidden in view and remains available while
  editing; it stays in the document model.
- New registered layouts automatically enter the matrix. Supply a useful
  editor default and add regression cases for its capacity limits, content
  migration and important geometry. The matrix uses common example content;
  it does not replace a realistic scenario or the layout's maximum-capacity tests.

## Checks and visual review

```bash
node box_agent/skills/document-skills/pptx/scripts/render_theme_matrix.js --out '<PRESENTATION_DIR>/qa/pptx-full-theme-review' --check --screenshots
```

Without filters this discovers every current theme and layout dynamically.
It checks style/field contracts, renders a deck per theme, runs the existing HTML
and runtime probes and writes `matrix.json` plus a four-column gallery. Geometry,
contrast and text-fit warnings make the maintenance command fail. Browser
screenshots are optional: omit `--screenshots` on a machine that cannot capture
them; omit `--check` for a source-only gallery build. Missing browser evidence
must be reported as unverified, never as a successful visual review. This matrix
is a maintenance tool, not a mandatory stage of every user deck generation.

Compare short, ordinary and dense content. Inspect every theme's identity and
representatives of every layout. Preserve image context, units, counts and
diagram relationships. Actual text clipping still fails even when a component
has decorative arrowheads extending beyond its own container. Such decorations
are allowed only when contained within the slide and real content fits.

For repository changes, also run the focused presentation-system, controlled
deck, export, skill-loader and generated-manifest tests; regenerate the builtin
skill manifest with the repository's `scripts/generate_skills_manifest.py`.
Report source checks separately from runtime build/install/restart and live
desktop verification. HTML checks do not prove PowerPoint font substitution.

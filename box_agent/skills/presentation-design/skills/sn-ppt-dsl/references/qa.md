# 成品验收

## 程序检查范围

`build` 检查 XML、导出文字与图表数据。原生图表的分类、系列名和值须同时与源 XML、OOXML 图表缓存及内嵌工作簿一致。这里只证明导出保真；统计口径、引用和事实正确仍须回到材料核对。

`preview` 渲染真实 PPTX，按页比较原生文字与 PDF 文字，覆盖中文、英文、拼音、数字和单位。正常换行与 Unicode 等价编码不会视为缺字。缺字或数值变化会阻止预览交付，并在 `qa/rendered-text.json` 指出具体页码；抽取顺序变化只列为风险，需看原尺寸页确认，不能凭报告直接改版。

## 看图与记录

1. 用 `contact-sheet.png` 看整体风格、节奏与素材重复情况；它不能替代小字阅读。
2. 按 `manifest.json.batches` 看清晰的 2～4 页审阅图，完成全页覆盖。关注图片是否完成页面任务、正文可读、实际换行、遮挡、裁切和图表标签。只有一页时审阅图包含该页。
3. 对疑似问题及 `risk_pages` 看原尺寸 `slide_NN.jpg`，必要时用宿主图像能力查看局部。风险页登记结论时必须包含对应的单页图证据。`chart_rendering` 表示图表标签需目视检查，`text_flow` 表示抽取文本不连续；它们不是已确认的缺陷。
4. 实际看过后记录具体页码、所看的预览图文件名和具体观察。`contact-sheet.png` 仅供全局扫视，不能作为逐页通过证据；非风险页用至多四页的 `review_batch_NN.jpg` 或原尺寸 `slide_NN.jpg`，风险页必须用原尺寸单页图。每次 `review` 最多记录四页，`--evidence-image` 可重复传入，但每个页码须由对应图片覆盖；按批次分别写具体观察。不要因为程序通过、图片生成成功或哈希匹配就声称已做视觉检查。

```bash
python "<SKILL_ROOT>/scripts/dsl.py" review "<DECK_DIR>/presentation.pptx" --pages 1 2 --status pass --finding "标题正文清楚，无遮挡或裁切" --evidence-image review_batch_01.jpg
python "<SKILL_ROOT>/scripts/dsl.py" review "<DECK_DIR>/presentation.pptx" --pages 5 --status fix --finding "图表标签被折线穿过，需调整标签位置" --evidence-image slide_05.jpg --source-file slides/slide_05.xml
```

`review` 命令只记录当前 Agent 的视觉结论，不调用视觉模型。审阅图或单页已经看清且未变化时不重复加载；画面无法辨认或发现实际问题时才放大、复查，不用固定调用次数代替质量判断。

在 Box-Agent 中，最终验收图用 `inspect_images(..., strategy="proxy")` 查看。Harness 只把成功返回的代理看图调用计入可核验记录；当前原生图片路径还没有“已送入模型并得到有效回应”的完成记录，不能用它声明 Harness 验收通过。每次最多送入当前需要检查的图片，避免重复看未变化页面。


## 层级与阅读顺序的成品判断

静态零错误只说明程序检查通过。看实际 PPTX 预览时，对每页分别判断：

- 标题辨识：页面标题在哪里，正文从哪里开始；装饰、编号或其他强调是否让标题难以识别。
- 正文层级：主结论、支撑信息、辅助说明是否区分清楚；同级信息是否一致，是否有多个互相竞争的焦点。
- 阅读顺序：主要信息从哪里开始，分成哪些组，各组按何种关系阅读；流程/对比/图表是否需要反复寻找下一处信息。
- 跨页一致性：与本册设计基线相比，同类页的标题位置、字阶与强调方式是否稳定；例外是否服务于内容。

review 的 finding 对所登记的每页写明具体标题/正文位置、主次关系和阅读路径；不能仅写“标题正文清楚”。发现问题时指出页码和相应元素/区域，按既有 fix → repair-start → 修改 → build → preview → 复验流程处理，仍遵守每页最多两次返修。实际看不清或预算用尽时保留问题，不能因记录齐全而判 pass。字号比例和抽取顺序只可提示风险，不能替代看图结论。

## 成品逻辑复核

把逻辑复核并入已有全页看图：使用与当前 PPTX 哈希匹配的预览，先从实际标题、正文、图表和箭头中定位疑点，再回查 `outline.md`、用户材料或已有 Research。不要用大纲中的“已区分”“已追证”为成品背书；同一 Agent 的复核也不称为独立审阅。已看清且未变化的图片可以复用，不额外固定一轮看图调用。

- **结论与依据**：区分材料事实、推断与方案建议，不把假设写成已证实效果。每页实际主张是否得到相应依据支持，适用范围是否一致？比较要核对对象、时间、单位、分母、评分口径与必要前提；尤其留意“最难”“因此有效”等强判断。限定条件须覆盖标题、正文、图注和相关总结，不能只加脚注、改标题而保留相冲突的断言。不同口径不必禁止同页展示，但不能直接据此排出难度或因果。
- **图示与关系**：箭头和位置在表达先后、因果、分支还是并列？逐条核对关系是否有依据；状态流程中的触发、退出、恢复路径是否与内容一致。没有先后依据的并行项应改为并列或分区；真正的流程保留顺序，不把所有箭头一律删除。
- **全册承接与增量**：按最终页序串起实际主张，结尾是否回应目标、建议是否有前文依据？跨章节对照同主题页：拿掉某页具体会失去哪条必要信息？用实际正文验证增量，不能只靠“概览/证据/总结”角色标签保留重复。不同职责的导航、详细依据和备查允许复现主题；有缺环时补已有依据、收窄结论或保留待验证条件，不用过渡句填补证据。

先找疑点，再判断是否成立；不能看到熟悉的版式就自动判错。对疑点定位到页码、原句/图形区域及相关页，回查具体材料段落、表格或图示，区分“有证据的缺陷”和“尚不能确认的风险”。成立时在现有 `review --finding` 中说明冲突、修复动作及修后应看到的结果，逐页登记 `fix`；排除疑点也写出具体依据。不另建逐页审查报告，不要求每页重复展开上述三项长评语。

实现偏离大纲时由 DSL 修正对应 XML；需要改变大纲标题、核心结论、页序或页数时返回 Story，修改同一 `outline.md` 后再生产。新事实仍需按 Entry/Story 的证据路径补齐，不得为完成验收临时编证据。局部修复沿用现有 `fix → repair-start → 修改 → build → preview → 复验` 和每页最多两次预算；涉及增删页的内容问题须另行规划，不冒充局部修复，也不重置旧预算。

修复后确认原问题已从新版画面消失，并回查与该主张相关的标题、正文、图注、前后承接及非相邻总结，防止只改一处、其他位置仍矛盾；只重看受影响的内容和必要图片。关闭问题的 finding 写明实际变化及关联页核对结果，不能仅写“逻辑已优化”。未改图片可复用看图证据，但旧语义判断不能代替本次关联核对；相关页需改动时也须逐页登记。无法核实且影响关键结论、预算用尽或缺环未解时保留问题和 `partial`，不能因 `verify` 或 Harness 返回 `passed` 就宣称全册逻辑已通过；现有程序不自动验证这些语义判断。

## 视觉表达是否完成任务

在已有逐页 finding 中，针对承担解释或证据任务的图，指出实际能看见的特征和它如何支持本页结论；仅“有图片、风格统一”不足以证明解释有效。检查条件分支/并行关系是否被箭头改成固定顺序、图片裁切是否藏住关键动作、数据图是否保留正确时间/分母。氛围图按气氛角色判断，不强求其证明事实；以文字或数据图已能清楚完成任务的页面不因缺照片判差。

预期特征看不见或图形表达了错误关系时，登记具体图/区域与未完成的理解任务，使用现有返修流程和每页最多两次预算处理。不得用补一张同主题图片、改成“装饰”标签或删去重要条件，把未解决的解释缺口记为通过；无法修复时如实保留。

## 修改后复查

看到具体问题后，修改 `slides/slide_NN.xml` 或该页引用的素材。对任务目录构建成功后，脚本按源文件和已用素材的实际变化登记每一页的返修。共用素材变动会涉及所有使用页。也可以先登记观察并用已有的 `repair-start` 启动返修，两种顺序共用每页两次的预算。构建失败保留上一次可用成品，自动登记只在成功构建时计数。保留用户确认的页序和页数。

```bash
# 修改页源后，构建成功再生成本次预览
python "<SKILL_ROOT>/scripts/dsl.py" build "<DECK_DIR>" && python "<SKILL_ROOT>/scripts/dsl.py" preview "<DECK_DIR>/presentation.pptx"
# 实际查看本次预览返回的图片，再记录所见
python "<SKILL_ROOT>/scripts/dsl.py" review "<DECK_DIR>/presentation.pptx" --pages 5 --status pass --finding "图表标签已避开折线" --evidence-image slide_05.jpg
```

重建后只复查受影响页。新渲染仅在页码、单页 PNG 和所用审阅图的哈希都相同时复用旧结论；若同批审阅图改变，同批其他页也列入 `pending_pages`。没有完成源文件修改、重建、当前预览复查三步时，待修页不能记为 `pass`。

分批图、单页图、PPTX 哈希、页码覆盖和每页所看的证据图保存在 `preview/manifest.json` 和 `qa/visual_review.json`。预览重建会删除脚本管理的旧页图和旧分批图，保留目录内用户另放的文件；渲染失败保留上一次预览。

预算用尽后，`repair_ledger.json` 保留未解决问题。保留当前可用 PPTX，说明页码、问题和已用次数；`visual_review` 和任务状态记为 `partial`。

首次预览使用 `preview/`；重建 PPTX 后，默认入口自动选择新的 `qa/previews/pptx-*` 目录，避免覆盖已看过的图片。当前 PPTX 和有效预览都未变化时，`preview` 复用现有文件，不再重复渲染。`review` 默认使用当前预览；若手动指定 `--output`，两个命令须使用同一路径。最终运行 `dsl.py verify`，确认 `visual_review=passed`、无 `fix_pages` 和 `pending_pages`，再调用 `publish_artifact`。只有 Harness 的看图证据门禁也返回 `passed`，任务状态才变为 `complete`。`partial/needs_fix/stale` 均不能声明全部完成。图片哈希只证明审阅对象一致；Harness 要核对 `inspect_images` 的实际成功调用。

`qa/visual_review.json` 中的 `preview_directory` 按 PPTX 所在目录保存相对路径。`preview` 和 `review` 的相对 `--output` 也以 PPTX 所在目录为基准；移动整套任务目录后，仍按同一规则找到预览。运行时不写死某个用户的绝对目录。

旧版无证据或空结论的 `pass` 记录在重新预览后不会复用；它们不能作为新验收通过的证明。图像文件与哈希只能证明审阅对象一致，不能证明模型确实阅读了图片；后续可由 Harness 关联 `inspect_images` 调用记录。
